# 開工前先查有沒有人做過

## 為什麼

- 自己從零寫一個已經有成熟開源版本的東西，最花時間也最容易有 bug；反過來，找到的東西授權不能用
  （GPL 會讓整個 App 跟著開源、沒附授權就是不能抄），或根本不支援台股、手機，硬套反而更慢。
- 同一個點子以前可能評估過、測過沒用。沒查就會重做一次。

## 照這個順序查（便宜的先，查到就可以停）

1. **自己的紀錄**（不花額度）：
   - 這個 App 的 `CLAUDE.md`、`docs/`（例如 `DECISIONS.md`、`EXTERNAL_REVIEWS.md`）：以前做過、測過、拒絕過嗎？
   - skl 技能庫：`/tmp/skl`（照 app-bootstrap 的方式取得）裡搜 `SKILL.md` 的 description、
     `community/README.md` 的「評估過沒收的」、`web/ideas.json` 的點子。已經有的技能直接用 app-bootstrap 裝。
2. **GitHub**：用英文關鍵字搜（中文點子先換成英文詞），看星數、`pushed_at`（一年內有更新）、授權。
   - 有 GitHub 搜尋工具（MCP）就用；沒有就打 `https://api.github.com/search/repositories?q=...&sort=stars`，
     Token 只放 HTTP 標頭。搜尋 API 未登入每分鐘只有 10 次，⛔ 不要連續狂打。
   - 使用者也可以在手機上用 Repo X-Ray（`https://xin7355-collab.github.io/skl/xray.html?q=關鍵字&fz=1`）看。
3. **套件庫**：npm（`https://registry.npmjs.org/-/v1/search?text=...`）、PyPI（用網頁搜尋）——只在要找「拿來用的函式庫」時查。
4. **台灣特有**：要台股、繁中、台灣法規的，另外查有沒有台灣版本；國外的東西常常沒有證交所／櫃買資料。

## 每個候選要看（最多 5 個，看程式不只看 README）

| 欄位 | 怎麼看 |
|---|---|
| 實際在做什麼 | 讀主要程式檔，不是 README 宣稱的 |
| 維護 | 最近一次 commit、還有沒有人回 Issue |
| 授權 | 看 LICENSE 檔本身：MIT／Apache／BSD 可以用；GPL 抄了整個 App 要跟著開源；沒有 LICENSE 檔 = 不能抄 |
| 合不合用 | 支不支援台股／繁中、手機（iPhone）能不能用、要不要付費 API |
| 可信度 | 有宣稱準確率、報酬的，看有沒有樣本外驗證、有沒有跟「買進持有」比；沒有就當沒說 |

## 結論只有三種（照規則，不憑感覺）

- **直接用**：授權可用、一年內有更新、涵蓋需求八成以上 → 裝它／用它，⛔ 不要重寫。寫清楚放哪、怎麼更新。
- **參考後自己做小的**：有類似的，但授權不能用、沒維護、或不支援台股／手機 → 只借想法（不抄程式碼），
  列出「我們要做、它沒有的」2～3 點，做第一版就好。
- **放心做**：找不到像樣的 → 照原計畫做，先做最小的第一版。

## 回報格式（手機好讀）

1. 一句結論（三種之一）＋理由。
2. 表格最多 5 列：名稱（連結）｜星數｜最近更新｜授權｜一句話（從程式看）｜合不合用。
3. 下一步要做什麼。
4. **記下來**：寫進這個 App 的決策紀錄（例如 `docs/DECISIONS.md` 加一節「外部參考評估：…」，結論寫在標題），
   下次同一個點子先查這裡，不重查。

## 不要做的事

- ⛔ 不要只看星星數就決定；⛔ 不要把找到的程式碼整段貼進來而沒看授權。
- ⛔ 不要為了查而花錢（付費 API、付費搜尋）；查不到的寫「沒查到」，不要猜。
- 小修改、修 bug、改文字不用跑這套，直接做。
